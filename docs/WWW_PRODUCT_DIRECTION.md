# WWW 제품 방향

상태: 제품 목표. 구현 완료 여부는 아래 표로 구분한다.

## 목적

WWW는 사용자가 고른 AI 모델로 작업하고 그 과정을 관찰하는 독립 터미널 도구다. 오케스트레이션은 적절한 모델로 요청을 보내고, 필요한 때에만 다른 관점을 얻고, 실패나 전환의 경위를 사용자가 알 수 있게 하는 역할을 맡는다. 업무 방법론이나 일곱 단계 절차를 모든 요청에 적용하지 않는다.

## 사용자 계약

| 관심사 | 목표 동작 |
| --- | --- |
| 주 모델 | 사용자가 선택한다. 세션에서 실제 사용한 provider와 모델을 표시한다. |
| 여러 구독권 | 각 계정의 인증·사용 가능 상태를 독립적으로 확인한다. 연결되었다는 이유만으로 모두 호출하지 않는다. |
| 교차검토 | 사용자가 요청하거나 명시한 정책에 맞을 때만 실행한다. 가능하면 주 작성자와 다른 provider를 사용하며, 검토자를 표시한다. |
| 실패 대체 | 재시도 가능한 실패에만 사전 설정된 후보로 전환한다. 원래 모델, 실패 이유, 실제 응답 모델을 남긴다. 조용한 전환은 허용하지 않는다. |
| 화면 | `UNDERSTAND · WORK · RESULT`와 `PLAN · PROGRESS · TEST`로 관찰 가능한 사실을 보여준다. 짧은 요청에는 불필요한 단계를 만들지 않는다. |
| 확인 | 실행 성공, 테스트 결과, 검토 의견을 구분한다. 확인하지 않은 결과를 완료라고 추정하지 않는다. |

WWW는 숨겨진 모델 추론을 수집하거나 노출하지 않는다. 도구 호출, 응답, 오류, 사용량처럼 실제 제공된 신호만 표시한다.

## 제품 경계

WWW에 필요한 것은 얇은 모델 연결·인증 계층, 대화 실행, 관찰 표면이다. GJC의 provider/auth 구현은 필요한 부분과 라이선스 고지를 검토해 선별적으로 가져올 수 있다. GJC 전체 agent loop, OMO, OMX, Pi coding agent의 방법론·역할·훅·스킬 묶음은 WWW의 배포 단위가 아니다. 현재 의존성과 코드는 이 목표로 이전 중이므로, 패키지에서 제거하기 전에는 실제 import와 실행 경로를 확인한다.

`woo-entry`와 Linear·Obsidian·RPA 기록 스킬은 WWW 사용 기능이 아니라 WOO 개발 체계다. 전역 WES의 정본과 충돌을 확인하고 그쪽으로 옮긴다. 제품 패키지에는 사용자 실행에 필요한 코드와 안내만 포함한다.

## 구현과 목표의 차이

| 영역 | 현재 | 다음 수락 조건 |
| --- | --- | --- |
| 기본 실행 | Codex 중심 Workbench | 사용자가 고른 provider/model로 같은 WWW 화면에서 실행 |
| 다중 모델 | 별도 `www router` 경로 | 기본 화면에서 인증·선택·실제 응답 모델 확인 |
| 검토 | 분리된 ReviewService, 기본 검증 요구 설정 | 선택적 교차검토와 검토 모델·결과 표시 |
| 대체 | 경로별 재시도 구현 | 전환 사유와 실제 모델을 한 실행 기록으로 표시 |
| 배포 | private Bun 패키지, 내부 스크립트 혼재 | 라이선스·배포물·설치 경로를 확정하고 내부 도구 분리 |

구현되지 않은 행을 현재 기능으로 홍보하지 않는다. 이 문서의 목표 계약을 기준으로 코드와 공개 문서를 순차적으로 정리한다.
