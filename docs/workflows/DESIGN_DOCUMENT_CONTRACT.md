# Design Document Contract

- 상태: 장기 Workflow Contract
- 적용 대상: 구현 전에 고비용 결정을 드러내고 검토해야 하는 제품·시스템 변경
- 상세 정본: [Obsidian 상세 정본 계약](../planning/linear-development/OBSIDIAN_CANONICAL_CONTRACT.md)

## 목적

디자인 문서는 구현 설명서가 아니다. 틀렸을 때 되돌리기 어렵거나 손실이 큰 결정을 구현 전에 드러내고, 다른 사람이 목적·경계·위험·대안을 검토할 수 있게 하는 계약이다.

WWW는 별도의 경쟁 정본을 만들지 않는다. 디자인 내용은 Obsidian 상세 정본의 `draft`에서 작성하고, 실행 범위와 일정은 Linear, 실제 구현과 테스트는 Git, 실행 결과는 Evidence와 Receipt가 소유한다.

## 언제 필요한가

새 capability 또는 기존 계약 변경을 시작할 때 다음을 확인한다.

- 여러 사람·Agent·provider·도구가 구현을 나누어 수행하는가?
- 구현이나 이관이 장기간 이어지거나 여러 release에 걸치는가?
- API·schema·저장 형식·identity·권위 경계처럼 나중에 바꾸기 어려운가?
- 목표·요구·책임 경계가 모호한가?
- 다른 팀·저장소·서비스·업무 원본과 조정해야 하는가?
- 보안·개인정보·법적 위험, 데이터 유실, 중복 외부 쓰기처럼 설계 시점에 막아야 할 큰 실패가 있는가?

하나라도 해당하면 디자인 검토의 가치가 있는 것으로 본다. 둘 이상이거나 마지막 항목에 해당하면 구현 전에 상세 정본 `draft`와 독립 검토가 필요하다. 모두 해당하지 않고 잘못 선택해도 짧은 시간 안에 안전하게 되돌릴 수 있으면 Linear 이슈와 테스트만으로 진행할 수 있다.

기존 capability의 작은 변경은 새 문서를 만들지 않고 기존 상세 정본의 영향받는 계약과 결정을 갱신한다. 새 문서 발급 여부는 변경 파일 수가 아니라 capability 책임의 분리 여부로 판단한다.

## 얼마나 자세히 쓸 것인가

결정을 넣을지 판단하는 기준은 **틀렸을 때의 비용**이다.

- 되돌리기 어렵고 파급이 큰 선택은 근거·제약·대안·실패 조건까지 기록한다.
- 쉽게 교체하거나 사용자 피드백 뒤 짧게 수정할 수 있는 구현 세부사항은 문서에서 제외한다.
- 아직 알 수 없는 값은 추정으로 확정하지 않는다. 미결 질문으로 남기고 필요한 관측과 다음 행동을 적는다.
- 모든 선택지를 장황하게 보존하지 않는다. 실제로 유력했던 대안과 기각 이유만 남긴다.

문서 길이 자체는 품질 기준이 아니다. 독자가 구현 전에 잘못된 방향을 발견하고, 구현자가 추가 추측 없이 고비용 결정을 따를 수 있을 만큼만 작성한다.

## WWW 정본 매핑

| 디자인 내용 | WWW의 소유 위치 |
|---|---|
| 한 문장 목적·배경·관련 원본 | Obsidian `1. Intent` |
| 목표·비목표·인접 책임 경계 | Obsidian `1. Intent`, `2. Scope` |
| 사용자 시나리오·측정 가능한 품질 목표 | Obsidian `3. Desired Behavior`, `10. Acceptance Contract` |
| 용어·불변식·주요 제약 | Obsidian `4. Domain Contract` |
| 상태·데이터 흐름·편집 가능한 다이어그램 | Obsidian `5. State Model`, `6. Data & Runtime Flow` |
| API·CLI·파일 형식·의존성·신뢰 경계 | Obsidian `7. Identity & Persistence Contract`, `8. Integration Contract` |
| 보안·개인정보·법적 위험·로그·복구 | Obsidian `6`, `9`, `11`의 해당 계약 |
| 미결 질문·결정·대안·승인 근거 | Obsidian `14. Decisions & Evidence` |
| 구현 위치 | Obsidian `12. Implementation Map`의 파생 정보 |
| 일정·Milestone·현재 실행 상태 | Linear 링크. Obsidian에 복제하지 않음 |
| 코드·테스트·로그·실행 결과 | Git과 Evidence/Receipt 링크. Obsidian에 전문을 복제하지 않음 |

관련 없는 절을 내용으로 부풀리지 않는다. 해당 위험이 없으면 검토한 범위와 해당 없음의 근거를 짧게 적는다. 다이어그램은 데이터 흐름, 책임 관계, 외부 의존성처럼 산문보다 관계를 빠르게 보여줄 때만 사용하며 재생성 가능한 원본을 함께 보존한다.

## 미결 질문과 결정

미결 질문은 `14. Decisions & Evidence`에 다음을 남긴다.

| 필드 | 의미 |
|---|---|
| Question | 아직 결정할 수 없는 문제 |
| Cost of Wrong | 잘못 결정했을 때의 손실과 되돌림 비용 |
| Options | 현재 유력한 선택지 |
| Next Evidence | 결정을 위해 필요한 조사·실험·사용자 판단 |
| Owner | 다음 행동의 책임. 일정이 필요하면 Linear 업무를 연결 |
| Blocking | 이 질문이 구현 또는 수락을 막는지 여부 |

질문이 해결되면 삭제하지 않고 같은 절의 Decision으로 옮긴다. 선택, 이유, 실제로 검토한 대안, 영향받는 계약, 결정자·결정 시각, 근거를 남긴다. 조사·테스트 통과와 사람의 결정 승인은 서로 다른 사건이다.

## 리뷰와 활성화

```text
Design triage
  ├─ 문서 불필요 → Linear → 구현 → 검증
  └─ 문서 필요   → Obsidian draft → 미결 질문 해소 → 독립 리뷰
                                           ↓
                                      active 계약
                                           ↓
                                  Linear 분해 → 구현 → 검증
```

- 작성자와 최종 검토자는 다른 패스여야 한다.
- 리뷰는 문장 취향보다 목적, 책임 경계, 고비용 결정, 실패·복구, 누락된 대안을 본다.
- 구현을 막는 미결 질문이 남아 있으면 관련 계약을 `active`로 전환하지 않는다.
- 검토 결과는 Decision 또는 Review Evidence로 연결하고 검토자와 시각을 남긴다.
- `active`는 현재 채택된 디자인 계약이라는 뜻이지 구현 완료나 사용자 수락을 뜻하지 않는다. 구현 수락은 Acceptance 상태와 Evidence가 별도로 소유한다.
- 구현 중 전제가 깨지면 조용히 코드를 맞추지 않고 상세 정본을 `draft`로 개정해 같은 검토 흐름을 다시 적용한다.

현재 이 디자인 리뷰는 문서·스킬이 집행하는 방법론 게이트다. `obsidian:check`가 미결 질문이나 리뷰 내용을 자동 판정한다고 주장하지 않는다.

## 완료 조건

디자인 단계는 다음 조건을 만족할 때 끝난다.

- 목적과 비목표가 평이한 언어로 설명된다.
- 틀렸을 때 비용이 큰 결정과 주요 제약이 드러난다.
- 사용자 동작, 인터페이스, 상태·데이터 흐름, 실패·복구 중 해당하는 계약이 정의된다.
- 구현을 막는 미결 질문이 없다.
- 유력했던 대안과 기각 이유가 남아 있다.
- 독립 검토와 필요한 사람 결정의 근거가 연결된다.
- Linear가 실행할 범위와 관측 가능한 완료 조건으로 분해될 수 있다.

이 조건은 구현·테스트·배포 완료를 뜻하지 않는다.
