# TUI 전체 Linear 요구사항·개발 준비 계획

2026-09-06 계층 정정: 아래 최초 계획·실행 이력의 WOO-674 직계 T-note/Composer 배치는 대체됐다. 현재 WOO-693·694는 Chat(WOO-679) 아래에 있으며 Workbench 직계는 기존 Chat·Layout·Tracer·Todo 네 분류다. ID·본문·상태·Milestone은 보존했다. 이후 이슈 작업에는 [Linear Intake](../../../.agents/skills/woo-linear-issue-intake/SKILL.md)를 적용한다.

2026-09-06 계획 초안. 이번 패스는 계획만 작성하며 Linear 쓰기·제품 코드 변경은 수행하지 않는다. 대상은 WOO-673 아래 Workbench·Monitor·Dashboard·Stats다. 기존 v0.1.0 — First Public Release 마일스톤을 유지한다.

이번 응답의 산출물은 이 실행 계획과 읽기 전용 기준선이다. 아래 단계와 마지막 완료 조건은 사용자가 다음으로 실행을 지시했을 때 수행할 후속 작업을 설명한다. 신규 이슈의 UUID·URL은 실제 생성 뒤에만 채운다.

## 목표

사용자가 현재 실행을 이해하고, 편하게 입력하고, 결과와 근거를 찾아갈 수 있는 읽기 좋은 TUI를 만든다. 각 개발 이슈가 목적·현재 구현·남은 변경·수락 조건·코드 연결을 갖도록 Linear를 먼저 준비한다. 문서 작성 완료와 제품 구현 완료를 구분한다.

## 확인한 기준선

- Linear 프로젝트의 조회 목록 21건(취소 상태 포함)을 MCP로 조회했다. WOO-675/676/677 본문은 비어 있다. WOO-680/681/682에는 목적과 구현 시작점이 있지만 구체 검증 조건이 부족하다.
- WOO-673에 전체 화면 예시가 집중돼 있고, WOO-674에는 긴 데이터·journal 예시가 들어 있다. 부모는 목적·공통 원칙·통합 완료 조건으로 줄이고 예시는 해당 기능 또는 기술 문서에 이관한다. 기존 의미와 첨부를 먼저 보존한다.
- WOO-678 HUD는 Canceled이며 댓글은 없다. 과거 구조 감사에는 책임 중복으로 취소됐다는 기록이 있다. 자동 복원하거나 같은 이슈를 새로 만들지 않는다.
- Chat WOO-679/683/684/686~692는 이미 요구사항·부분 구현·실제 코드 ID가 연결돼 있다. 기존 내용을 재작성하지 않고 다른 영역과의 연결만 보완한다.
- 코드 시작점은 `runProjectWorkbenchShell`, `createDashboardLayout`, `TNotesSourceView`, `WorkspaceTodoView`, `WorkbenchMonitorView`, `RuntimeMonitorView`, `ObservabilityDashboardView`, `SessionStatsView`, `WorkbenchBottomHudView`다. 선언 존재는 구현 수락 증거가 아니다.

Chat의 WOO-692 검증은 재사용한다. Layout의 focus와 Chat의 스크롤, Tracer의 Source와 T-note의 참조, Monitor의 현재 상태와 Stats의 집계는 같은 요구사항을 양쪽에 복사하지 않고 소유 이슈와 관련 링크로 연결한다.

Todo는 특히 Native Plan projection과 legacy Todo.md 경계를 다시 확인한다. 인증·Repository·Router overlay 파일의 존재만으로 Native Workbench 기능으로 포함하지 않고 실제 shell 호출을 추적한다.

Composer 신규 후보는 먼저 Chat 이슈의 전송·대기·오류 조건과 항목별 대조표를 만든다. 입력 편집·dispatch는 Composer, 생성된 답변 보존·표시는 Chat, 공통 focus는 Layout으로 소유권을 정하고 미소유 요구만 신규 후보에 남긴다.

## 이슈 본문 규칙

부모 이슈는 목적, 공통 원칙, 통합 완료 조건만 남긴다. 하위 이슈 목록을 본문에 다시 만들거나 모든 화면 책임을 반복하지 않는다.

실행 이슈에는 다음 다섯 항목을 쓴다.

1. **목적:** 사용자가 겪는 문제와 바뀔 경험.
2. **동작·완료 조건:** 정상·빈 상태·실패·취소·재개 중 해당되는 조건을 관측 가능한 문장으로 작성.
3. **개발 현황:** 확인한 구현, 확인한 테스트, 부족한 동작, 아직 확인하지 않은 부분.
4. **코드 연결:** 실제 파일·선언과 재사용 지점. 존재하지 않는 API나 단축키를 구현된 기능처럼 안내하지 않는다.
5. **검증:** 실행 시나리오, 기대 결과, Evidence 위치. 실제 화면과 자동 검증을 구분한다.

화면 ASCII·상세 JSON은 요구를 이해하는 데 필요한 사례만 남긴다. 기술 전문은 Git 문서로 연결한다. 제목은 한국어 결과 문장으로 쓰고 종류·영역은 라벨로 찾게 한다.

## 라벨과 상태

- 기존 `Chat`, `UX`, `Reliability`, `Testing`, `perf`, `Bug`, `Feature`, `Improvement`를 재사용한다.
- 영역 필터용 `TUI`, `Layout`, `Tracer`, `Todo`, `T-note`, `Composer`, `Monitor`, `Dashboard`, `Stats`를 후보로 둔다. 실제 이슈 배치 후 필요한 것만 중복 조회하여 만든다.
- 영역 + 변경 성격을 조합한다. 실제 재현 결함에 Bug, 독립 통합 검증에 Testing을 사용한다.
- 기존 `status:*` 라벨을 새로 적용하지 않는다. 상태는 Linear 상태 필드가 소유한다.
- 본문이 채워졌다는 이유로 진행 중·완료로 바꾸지 않는다. 코드와 검증을 대조한 근거가 있을 때만 제안하며, 미검증은 명시한다.

## 진행 순서와 산출물

1. **현재 상태 보존:** 프로젝트·마일스톤·이슈 본문·관계·라벨을 재조회하여 scratchpad에 저장한다. 조회 전체 목록에 유지/축약/보완/범위 밖의 처리를 기록한다. WOO-671 Workflow·672 System은 범위 밖으로 유지하되 의존 참조만 검토한다. 현재 브랜치·HEAD·미커밋 파일 기준을 기록한다.
2. **코드와 요구 대조:** Layout/입력/상태/T-note/Todo/Tracer 조사와 Monitor/Dashboard/Stats 조사를 병렬 수행한다. 실제 Native shell 경로와 legacy 경로를 구분하고 각 결과를 파일로 회수한다. 각 조사는 실제 진입점, 입력·원본·projection, 상태 전환, 기존 테스트, 미검증 요구에 답한다. 지표는 화면이 실제 소비하는 데이터 계약과 대조하고 제공되지 않는 값은 후속 의존 요구로 구분한다. WOO-672의 구체 작업이 선행임을 확인한 경우에만 blocked-by를 연결한다.
3. **Linear 초안 작성:** 기존 부모부터 책임 중복을 정리하고 각 화면의 실행 이슈 후보를 쓴다. 한 이슈는 독립적으로 검증 가능한 변경 단위로 나누며, 영역마다 같은 개수의 하위 이슈를 강제로 만들지 않는다. 반영 대상의 신규/수정 이슈 수·제목·부모·신규 라벨을 목록으로 고정한 뒤 검토하며, 범위를 추가하면 이 목록부터 갱신한다.
4. **독립 검토:** 영역별로 묶어 Sonnet 읽기 전용 검토로 요구 누락·코드 오인·수락 조건을 확인하고, Opus 최종 감사로 전체 중복·범위 확대·허위 완료를 확인한다. 지적을 반영한 뒤 영향받은 부분을 재검토하고 미해결 사항은 남긴다. 미실행 검토는 미실행으로 기록한다.
5. **Linear 반영:** 확정된 초안을 반영하기 직전에 다시 읽어 동시 변경을 대조한다. 기존 ID·마일스톤·관계를 보존하고 신규 이슈는 Linear가 발급한 ID를 사용한다. 생성/변경 후 본문·라벨·부모·마일스톤을 재조회한다.
6. **코드 ID 연결 준비:** 각 이슈의 실제 UUID·URL과 구현 선언·테스트·Evidence를 대응표로 만든다. 후속 코드 연결 패스에서 `@linear WOO-...`와 기존 원장을 확장한다. 이번 요구사항 정리 중 제품 동작을 변경하지 않는다.
7. **개발 순서 확정:** 공통 Layout/focus 계약 → Chat 보존·thread 격리 결함과 Tracer 연결 → Todo/T-note/입력·상태 → Monitor → Stats/Dashboard → 전체 화면 수락 순으로 의존성을 검토한다. 데이터 제공이 필요한 항목은 WOO-672와 관련/선행 관계를 검토하되 System 전체 요구를 대신 확정하지 않는다.

## 검증 조건의 공통 기준

- 40·80·120열과 폭/높이 변경에서 의미 있는 내용·조작 위치·읽던 위치가 유지되는지 확인한다. 실제 측정 전에 픽셀/행수/성능 수치를 임의 확정하지 않는다.
- 한글·emoji·긴 경로·빈 값·오래된 값·무채색 환경에서 역할·상태·생략을 구분한다.
- overlay 열기/닫기, 화면 전환, 세션 선택, 실행 중 입력·승인·중단 뒤 focus와 입력 내용의 기대 상태를 정한다.
- 숫자는 출처·기간·분모·측정 범위를 명시한다. 관측하지 않은 값을 0·100%·성공으로 꾸미지 않는다.
- Source는 같은 thread/turn/item을 가리키고, 원본 부재를 구분한다. provider 실행 완료·Todo 완료·업무 수락을 혼동하지 않는다.

## 계획 실행의 완료 조건

TUI 각 영역에 요구사항 소유 이슈가 있고, 실행 이슈에는 코드 시작점·남은 개발·관측 가능한 수락 조건이 있다. 중복 없는 라벨과 실제 Linear ID 대응표가 준비되며 반영 결과가 재조회된다. 실제 TUI 검증과 제품 개발의 미완료 항목은 그대로 남긴다. 코드 구현·커밋·배포와 v0.1.0 이후 Project View는 이번 정리의 완료 조건에 포함하지 않는다.
