# Linear 작업을 PR로 검토하는 개발 흐름

2026-09-06 사용자 결정. Chat을 파일럿으로 적용하고 TUI의 다른 기능에도 같은 흐름을 사용한다. 제품 목표는 www에서 입력·대화·계획·실행·근거를 이질감 없이 오가는 것이다.

## 무엇을 어디에 기록하는가

| 위치 | 역할 |
| --- | --- |
| Linear 부모 | 기능 목적·공통 원칙·통합 수락 조건 |
| Linear 하위 이슈 | 독립적으로 구현·검증할 결과와 수락 조건 |
| Linear 코멘트 | 변경 시점의 진행 상황, PR·검증 근거, 남은 조건 |
| Git PR | 실제 코드 diff, 재현·수정·검증 결과, Opus 검토와 후속 수정 |
| Git Evidence | 검증한 revision, 재현 절차, 결과·한계 및 상세 기록 |


Chat의 # T-note는 제품 안의 질문별 완료 요약이다. 개발 기록 매체와 구분하고 기존 Chat 범위에 유지한다.

검증 상세의 기준은 검증 대상 revision이 명시된 Git Evidence다. PR에는 검증 요약·Opus 판정과 Evidence 링크를, Linear에는 진행 요약과 해당 PR 링크를 둔다. 요약이 다르면 대상 revision의 Evidence를 대조해 정정한다.

이슈 본문에 진행 로그를 계속 덧붙이지 않는다. 기존 기록은 삭제하지 않고 날짜·revision·범위가 있는 코멘트로 정리한다. 오래된 테스트 통과 수는 현재 HEAD의 결과로 재사용하지 않는다.

## 한 PR의 절차

1. Linear 목적·하위 관계·기존 코멘트와 코드를 읽고 닫을 수 있는 변경 단위를 정한다. 부모 선정은 프로젝트의 Linear issue intake 절차를 따른다.
2. 다른 작업과 섞이지 않는 브랜치에서 결함을 재현하고 구현한다. 기존 미커밋 작업은 보존한다.
3. 코드 선언의 `@linear WOO-...`와 실제 이슈 UUID·URL, 코드·테스트·Evidence 위치를 연결한다. Unit은 기존 identity 계약을 확인한 뒤 사용한다. 어노테이션이나 연결의 존재가 구현 완료를 뜻하지 않는다.
4. 변경에 맞는 자동 테스트·타입 검사와 필요한 실제 TUI 검증을 수행한다. fixture·가짜 provider 테스트와 실제 Native TUI 검증을 분리한다.
5. **Opus가 읽기 전용으로 PR 변경과 검증 근거를 검토한다.** 이는 이번 세션의 사용자 명시 지시이며 일반 단계별 모델 기본값보다 우선한다. 리뷰에는 대상 commit SHA, 모델, 판정, 발견 사항, 미실행 범위를 기록한다. Opus를 사용할 수 없으면 미검토로 남기고 다른 모델의 통과로 대체하지 않는다.
6. 지적을 반영하고 바뀐 코드와 영향을 받은 검증을 다시 확인한다. 최종 PR head가 검토 대상과 다르면 미검토 차이를 명시하고 재검토한다.
7. PR 제목·본문에 Linear ID와 실제 이슈 링크를 넣고, Linear에도 PR 링크와 진행 코멘트를 남긴다. GitHub 자동 연동 여부를 실제로 확인하며 단순 URL 기록과 자동 PR attachment를 구분한다.
8. PR 생성·테스트 통과·merge·전체 이슈 수락을 분리한다. 부분 수정 PR에는 `Related to WOO-...`를 사용하고 전체 수락 전 자동 완료 문구를 쓰지 않는다. Merge는 별도 사용자 지시를 따른다.

## 진행 코멘트 형식

- 진행: 구현 전 / PR 검토 중 / 수정 중 / 검증 완료 / 남은 수락
- PR: 실제 URL 및 검증 대상 SHA
- 변경: 사용자에게 달라지는 결과
- 검증: 실행 명령·결과·Evidence 링크, Opus 판정과 검토 대상
- 남은 조건: 실제 TUI·외부 환경·다음 변경 등 아직 충족하지 못한 요구

기록 코멘트는 날짜·대상 SHA별로 추가한다. 오탈자·잘못된 링크를 정정할 때도 정정 사실을 남기며, 새로운 PR·검토 라운드로 이전 시점의 기록을 덮어쓰지 않는다. 기존 사용자 코멘트를 삭제하거나 덮어쓰지 않는다.
