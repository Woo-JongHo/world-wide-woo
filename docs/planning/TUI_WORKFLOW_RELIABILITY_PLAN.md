# TUI·Workflow 신뢰성 실행 계획

상태: 결함 수정·로컬 연결 구현 및 자동 검증 완료, 독립 감사·통합 결과는 개발 결과 문서 참조. 실사용 전. 2026-09-08.

사용자 요청: 제품 평가에서 제안한 세 작업을 순서대로 진행한다. 현재 범위는 TUI와 Workflow다. 평가 근거는 [제품·AI Engineer 평가](../research/WWW-PRODUCT-AND-AI-ENGINEER-ASSESSMENT-2026-09-08.md)에 둔다.

## 순서와 현재 작업

| 순서 | 작업 | 진입 조건 | 상태 |
|---|---|---|---|
| 1 | TUI의 계획 상태와 검증 결과를 일치시킨다 | 최신 변경 기준 확보 | 구현·행동 테스트 완료, 실제 Native 화면 미검증 |
| 2 | Workflow의 성공 판정과 저장 일관성을 보장한다 | 구현은 1단계 행동 검증 뒤 | 실패 기준선 고정 후 수정·회귀 통과 |
| 3 | 작은 Workflow를 두 프로젝트에서 끝까지 사용한다 | 연결 구현은 2단계 실패·복구 검증 뒤 | 로컬 fixture·CLI·TUI 배선 검증, 원격 전체 수락·실사용 미실행 |

단계마다 구현·자동 검증·실제 사용·독립 검토 상태를 별도로 기록한다. 단위 테스트 통과를 사용자 수락으로 바꾸지 않는다. 미래 WES, 신규 Provider, 범용 자체 Agent loop, 언어 재작성은 이 계획의 선행 조건이 아니다.

사용자 추가 결정: 각 단계는 **시나리오 작성 → 로컬 기준선 테스트 → 결함 수정·미구현 연결 → 같은 시나리오 재검증 → 실사용** 순서로 진행한다. 2·3단계의 제품 수정 순서는 유지하되, 독립적인 로컬 시나리오 작성·테스트는 1단계 완료 전에 병렬 수행한다. 실제 외부 도구 연결이 없는 시나리오는 미구현으로 기록하고 fixture의 상태 저장 성공을 업무 성공으로 바꾸지 않는다. 시나리오와 판정은 [Workflow 선행 테스트](WORKFLOW_PREUSE_SCENARIOS.md)에 기록한다.

## 1단계 — TUI 상태와 결과의 의미를 통일한다

### 출발점 정리

1. 편집 전에 현재 경로·브랜치·HEAD·dirty 파일을 다시 확인한다. 계획 작성 시 실제 브랜치는 dev이고 HEAD는 45aec4a였다.
2. [Native Plan 구현 인수인계](NATIVE_PLAN_TODO_TRACER_IMPLEMENTATION.md)의 변경을 읽는다. 문서는 다른 브랜치 이름을 적고 있으며 검증 미실행 상태다. 문서의 구현 완료를 검증 완료로 해석하지 않는다.
3. 진행 중 변경을 포함한 파일 digest와 diff를 고정한 뒤 감사의 `tui-repro.ts`를 재실행한다. 병행 편집으로 해당 파일이 달라지면 통합 기준을 다시 정한다. 기존 변경을 덮어쓰지 않는다.
4. 최신 코드에서 여전히 재현되는 문제를 실패하는 행동 테스트로 고정한다. 이전 908개 통과 기록은 최신 변경의 결과로 재사용하지 않는다.

### 구현 책임

- Native Plan의 항목 상태는 Native checklist revision이 소유한다. ExecutionRun의 도구 관측이 계획 상태를 추정해 덮어쓰는 경로를 제거한다.
- Todo와 Tracer는 같은 권위의 계획 상태를 사용한다. 공개 계획 문서는 표시할 수 있지만 실행 체크리스트로 자동 승격하지 않는다. 기존 source authority 변경을 활용한다.
- Native commandExecution의 수행 종료와 결과를 분리해 exitCode·출력·실패·취소·미확인을 보존한다. 도구 실패 뒤 복구 실행은 허용한다.
- 종료 요약에서 관측한 명령 결과를 잃지 않는다. 관측된 명령과 업무 검증 판정은 구분하고, 명령 이름만으로 업무 수락을 추정하지 않는다. 명시적인 검증 연결이 없으면 검증 판정은 미확인으로 남긴다.
- 기존 기록은 읽기 호환을 유지한다. 과거 근거가 부족한 기록에서 성공이나 검증 결과를 새로 만들어내지 않는다.

### 수락 시나리오

- Plan 진행 중 read·test 등 여러 도구가 종료돼도 Todo와 Tracer는 함께 진행 중이다.
- 명시적 Plan 완료 update 뒤 두 표면이 함께 완료된다. 도구 종료·turn 종료만으로 계획 완료가 발생하지 않는다.
- `item/completed + commandExecution + exitCode=1`이 결과 요약에 보존된다. 후속 성공이 있어도 앞선 실패 이력은 조회 가능하다.
- 검증 미실행·실패·결과 미확인을 구분한다. 실행 종료는 업무 수락과 구분한다.
- 계획 없음, 공개 Plan 문서, 여러 running 항목, 다른 turn·thread, 중복 사건, 취소·재개에서 계획을 발명하거나 다른 항목에 임의 귀속하지 않는다.
- 실제 터미널에서 요청 → 계획 → 명령 결과 → 종료 → 재개 흐름을 확인한다. 통합 대역 테스트와 실제 서버·화면 증거를 구분한다.

주요 경계: ExecutionRun reducer, ProjectWorkbench projection, Native Plan projection, 완료 요약. 경계 변경 시 LAYERS.md를 적용한다. 타입·아키텍처·관련 행동 테스트를 먼저 실행하고 변경 완료 시 전체 회귀를 한 번 수행한다.

## 2단계 — 성공 근거와 상태 저장을 함께 보장한다

먼저 Skill Runtime Contract와 저장소 호출자를 기준으로 거절·경쟁·저장 실패 시나리오를 작성하고 현재 코드를 테스트한다. 실패를 보존한 뒤 검증 결과의 발급자·소비자 및 저장 방식의 최소 설계를 고정한다. 이 상위 계획은 저장 형식 이관을 승인하거나 새 정본을 추가하지 않는다.

- 성공은 비어 있지 않은 문자열이 아니라 대상·revision·검증 결과에 결속된 근거를 요구한다. 검증 실행과 결과 확인은 Runtime이 소유한다.
- 사람이 승인한 대상과 현재 대상이 달라지면 승인을 다시 사용할 수 없다. 로컬 actor 표기와 독립적인 인간 승인 증명은 구분한다.
- revision 확인과 상태 변경을 하나의 동시성 경계로 묶는다. 상태와 Receipt는 함께 확정되거나 중단 후 복구 가능한 commit 절차를 사용한다.
- 과거 Receipt는 당시 기록으로 읽되 새 검증 기준을 통과한 것으로 소급 표기하지 않는다. 저장 형식 변경이 필요하면 이관·실패 복구·롤백 절차를 구현 전에 명시한다.

수락: 빈/임의 근거 성공 거절, stale 승인 거절, 실제 두 프로세스의 동일 revision 경쟁에서 한 건만 성공, 저장 단계별 장애·프로세스 중단 후 근거 없는 completed 부재, uncertain 재시도 차단 및 복구 안내. 감사 probe를 회귀 테스트로 발전시키며 write 순서만 뒤집는 수정은 수락하지 않는다.

## 3단계 — 한 Workflow를 두 프로젝트에서 완결한다

첫 대상은 현재 고정 chain 중 작은 `rpa-reconcile`이다. 착수 시 로컬 rpa-reconcile 스킬과 기존 검사 도구를 읽고 그 계약을 재사용한다. 처음에는 원격 수정 없이 정합성 검사·실패 보고·수락 기록을 끝까지 연결한다.

실사용 전에 두 임시 프로젝트로 Registry·chain·저장 격리·필수 입력 거절·재시작 시나리오를 먼저 실행한다. 실제 reconcile 검사와 TUI 연결이 없는 부분은 별도 미구현 시나리오로 유지하고, 연결 구현 뒤 동일 fixture에 검증을 추가한다.

- 두 격리 프로젝트에 동일한 Skill revision과 서로 다른 root·업무 ID를 적용한다. 업무 ID는 fixture임을 명시하며 실제 외부 ID를 발명하지 않는다.
- 요청부터 Runtime 실행·검증·Receipt·TUI 표시까지 하나의 호출 경로로 연결한다. 사용자가 성공 상태를 직접 전달하는 것으로 검증을 대신하지 않는다.
- 정상·필수 참조 누락·원본 변경·중단 재개·다른 프로젝트 참조 혼입을 두 프로젝트 모두에서 검증한다.
- TUI는 현재 단계, 근거, 차단 이유, 다음 행동을 같은 Run에서 보여준다. 원격 수집이 필요한 범위는 조회 시점과 실패를 기록하며, 원격 쓰기는 이 단계 기본 범위에 넣지 않는다.

수락: 같은 규칙이 두 프로젝트에서 같은 오류를 차단하고, 결과와 증거가 섞이지 않으며, 중단 후 재개에서도 결과가 보존된다. 임시 fixture 통과 뒤 실제 두 프로젝트의 읽기 전용 업무로 사용성을 확인한다. 실제 대상 프로젝트는 착수 시 사용자가 지정한 범위에서 고정한다.

## 완료 기록과 효과 측정

각 단계 결과에 코드 기준·재현 입력·예상값·관측값·검증 명령·실패·남은 작업을 남긴다. Codex가 저작·통합하고 반대 provider는 읽기 전용 검토만 수행한다. Sonnet·Opus가 사용 불가능하면 독립 검토 미실행을 유지하고 자동 대체하지 않는다.

3단계 뒤 동일 초기 상태와 수락 기준으로 Native+기존 규칙 경로와 WWW 경로를 비교한다. 반복 업무 5종×두 프로젝트의 10쌍을 초기 pilot으로 제안한다. 사람 확인 시간·재작업·잘못된 완료·실행 시간·Token을 기록한다. 품질을 낮추지 않고 확인 비용이 줄었을 때 다음 Workflow로 확장한다. 이 pilot은 장기 운영 신뢰성의 증명과 구분한다.

개발 변경과 최종 검증은 [개발 결과](TUI_WORKFLOW_RELIABILITY_RESULT.md)에 기록한다. 다음 단계는 사용자가 지정한 실제 두 프로젝트의 읽기 전용 pilot이다. 문서와 fixture 통과만으로 실사용 수락을 선언하지 않는다.
