# Linear에서 코드 수락까지

이슈 생성·분할·이동·본문 수정의 위치 판정과 등록 검증은 [Linear Issue Intake](../../../.agents/skills/woo-linear-issue-intake/SKILL.md)가 소유한다. 아래 논의 절차와 함께 적용하며, 기존 상위 분류를 늘리기 전에 부모·형제·하위 이슈를 대조한다.

상태: 논의용 실행 계약 초안. Linear 내용은 사용자와 하나씩 확정한다.

## 한 항목의 논의와 반영

1. MCP로 해당 Project/Milestone/Issue의 최신 본문과 관계를 읽는다.
2. 기존 코드·테스트·기술 문서·EP/ST·연결 원장을 대조한다.
3. 현재 내용과 발견한 충돌을 보여주고 수정 초안을 제시한다.
4. 사용자가 해당 내용을 결정한다. 한 번에 한 초점을 다룬다.
5. 반영 직전 다시 읽어 사용자가 논의한 이후 변경이 있는지 확인한다.
6. 합의한 내용만 적용하고 본문·ID·부모·Milestone·관계를 read-back한다.
7. 결정과 참조를 코드 문서·원장에 연결한다.

## 실행 Issue에 필요한 내용

- 사용자가 겪는 문제와 원하는 결과
- 포함 범위와 제외 범위
- 관련 Unit, 선행·관련 Issue
- 입력·원본·출처와 출력·상태 의미
- 현재 구현 위치·재사용할 코드·변경 후보
- 관측 가능한 수락 조건과 실패·취소·재개 조건
- 검증 시나리오와 Evidence 제출 위치

기능 Parent와 닫을 수 있는 변경 Issue의 역할은 ID 논의에서 확정한다. 단순 테스트 단계가 별도 사용자 가치를 갖지 않으면 Issue 체크리스트에 넣는 방안을 논의한다. 기존 Issue를 자동 삭제·취소하지 않는다.

## 코드 개발

논의가 끝난 Issue와 현재 Unit 연결을 읽고 시작한다. 코드가 이미 있으면 기존/부분 구현/미검증/누락을 구별한다. 필요한 부분을 이관하거나 구현하고, 해당 수락 조건과 기존 기능 회귀를 검증한다. 코드·테스트·Evidence·revision 연결을 갱신한다.

공통 API가 바뀌면 영향받는 다른 Unit과 Issue도 확인한다. 파일이 생겼다는 사실과 기능 수락을 구분한다. 실행기 success, 테스트 통과, 사람 수락은 서로 다른 사건으로 기록한다.

## 이번 기획이 완료되는 조건

- 제품 세 축과 공통/업무별 책임이 문서에 명시된다.
- v0.1.0의 범위와 세 Parent Issue의 닫힘 조건이 사용자와 합의된다.
- 첫 개발 항목은 추가 추측 없이 실행 가능한 수준으로 작성된다.
- Unit/Issue/기존 코드 연결 방식과 schema 이관 범위가 정해진다.
- 기존 문서의 충돌에 유지·대체·이력 보존 방침이 붙는다.
- Linear 반영 결과가 read-back되고, 아직 논의하지 않은 항목은 완료로 처리되지 않는다.

Opus 등의 검토는 결정 입력이다. 검토자가 제안한 scope·상태 enum·기능을 자동으로 release 필수 조건으로 승격하지 않는다.
