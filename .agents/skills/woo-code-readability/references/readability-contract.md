# WWW 가독성 계약

## 목표

코드를 행·열·셀로 비교하되 통일성은 **같은 역할을 같은 최소 구성으로 만드는 것**이다. 먼저 예외 때문에 길어진 구조를 제거·결속·정규화한다. 표형 정렬은 같은 역할의 비교 가능한 행이 3개 이상 연속될 때 적용한다. 두 행은 사용자가 비교 효용을 확인한 경우에만 표로 만든다. 120열은 새 구조의 분리 검토 신호이지 이미 수락된 정본 그리드를 해체하는 상한이 아니다. 정렬 자체가 목적이 아니며 구조를 줄일 수 있는데 공백으로 덮거나, 공백 때문에 의미 단위가 멀어지면 실패다.

통일성의 우선순위는 다음과 같다.

1. 같은 역할이 같은 구조와 읽기 순서를 갖게 한다.
2. 기본형에 섞인 이질 요소가 필수 계약인지 구조 누수인지 확인한다.
3. 의미와 타입 안전성을 보존하며 제거·내부 결속·정규화·표 분리로 구조를 간결하게 만든다.
4. 더 줄일 수 없는 실제 정보만 셀 데이터로 인정해 최소 폭으로 정렬한다.

여기서 `같은 최소 구성`은 의미를 잃을 때까지 축약한다는 뜻이 아니다. 행동·타입 안전성·도메인 책임을 보존하면서 제거할 수 있는 이질 요소만 없애며, 필요한 차이는 명시적인 계약으로 남긴다.

따라서 가장 긴 코드가 항상 정렬 기준은 아니다. 먼저 그 길이가 도메인 정보인지, 경계 정보인지, 구현 세부사항인지, 중복 표현인지 판정한 뒤 보존된 최장 데이터만 기준으로 삼는다.

## 위에서 아래로 읽는 역할 구조

- 기능 구현 파일은 소비자가 찾는 공개 기능을 먼저 두고, 개별 처리, 응답 변환·검증 순으로 세부 구현을 내려 배치한다. 조회 어댑터의 기준 예시는 `공개 기능 → 개별 조회 → 응답 변환`이다. 없는 역할을 채우려고 함수나 구획을 추가하지 않는다.
- 같은 역할의 함수는 같은 읽기 순서와 이름 체계를 사용한다. 선언 재배치 전 초기화·등록 순서 의존성을 확인하고 실행 순서는 보존한다.
- `opts`, `res`, `d`처럼 역할을 해석해야 하는 축약 이름은 `options`, `response`, `document`처럼 역할이 드러나는 이름으로 바꾼다. 컬렉션은 `placesById`처럼 내용과 조회 기준을 드러내며, 관용적 인덱스까지 기계적으로 길게 만들지는 않는다.
- 재사용은 같은 책임·입출력·실패 계약이 확인된 구현에 적용한다. 모양만 비슷한 조회·변환을 합쳐 호출 흐름을 숨기거나, 이름만 전달하는 래퍼를 늘리지 않는다.
- 이 구조 원칙을 Kotlin 등 다른 언어에 적용할 때는 해당 프로젝트의 선언·수명주기 규칙을 먼저 확인한다. TypeScript용 열 정렬과 검사 명령까지 그대로 이식하지 않는다.

## 그리드 모델

- **표**: 같은 문법 구조와 비교 목적을 가진 연속 코드 블록이다.
- **행**: 하나의 선언, 속성, import 또는 실행 흐름이다.
- **열**: `:`, `( )`, `{ }`, `< >`, `=>`, `from`, `= await`, `//`처럼 반복되는 문법 경계다.
- **셀**: 열 사이의 실제 식별자, 타입, 값, 실행문 또는 설명이다.
- **하위 표**: 셀 안에 `:` 같은 반복 구조가 다시 나타날 때 이름·구분자·타입으로 재분해한 내부 그리드다.
- **정렬 정책**: 비교 가능한 3행 이상의 연속 반복 블록을 최소 폭으로 정렬한다. 사용자가 수락한 두 행 표는 예외로 유지한다. 공개 Port에서 JSDoc이나 서로 다른 lifecycle 책임으로 끊긴 메서드는 하나의 표로 합치지 않는다. 사용자가 수락한 기준 파일의 `import`, `:`, `=>`, `case` 축은 보존한다. 반복 함수 표의 `( )` 내부 폭은 기존 공백이 아니라 실제 최장 인자값이 정하며, 짧은 값만 그 최소 폭 안에서 가운데 정렬한다.

## 확정 규칙

1. 한 번에 제품 파일 하나만 수정한다.
   사용자가 정본에 가깝다고 지정한 파일은 수정 대상에서 제외하고 비교 기준으로만 읽는다.
2. import는 runtime과 type 역할을 구분하고, `src` 내부 경로는 `@/` 별칭을 사용한다. named import에 값과 `type` specifier를 섞지 않고 별도 `import`와 `import type` 선언으로 분리한다. named specifier가 하나면 항상 한 줄로 두며, 둘 이상은 완성된 한 줄의 표시 폭이 120 이하일 때 한 줄로 접는다. 120을 넘을 때만 항목별 여러 줄로 내리고 닫는 `}`와 `from`은 같은 줄에 둔다. 같은 선언부의 한 줄 import는 실제 최장 선언부 기준으로 `from` 열을 맞춘다. 별칭을 새 경계에 적용하면 아키텍처 import graph도 함께 검증한다.
3. 같은 테이블 블록을 식별자, `:`, `( )`, `=>`, `{ }`, `< >`, `= await`, `from`, 우측 `//` 같은 문법 단위의 셀로 나눈다.
4. 각 셀은 같은 블록에서 가장 긴 실제 내용이 요구하는 최소 폭으로 통일한다. 기능·함수 식별자와 실행 셀은 왼쪽 정렬한다. 실제 최장 행보다 먼 임의 열은 만들지 않는다.
5. 괄호·중괄호·꺾쇠는 각각 독립된 외곽 경계다. 같은 비교 블록에서는 여는 기호와 닫는 기호의 열을 모두 맞춘다. 내부 폭은 가장 긴 실제 한 줄 내용으로 정하고, 짧은 값과 빈 값도 그 고정 폭 안에 둔다.
6. 타입 매개변수가 한 줄 폭을 120열 너머로 밀면 매개변수별로 줄을 나눈다.
7. 외곽 셀 안의 반복 문법도 비교 가능한 행이 2개 이상일 때 하위 표로 정렬한다. 함수 인자 셀은 실제 최장 값의 길이로 폭을 다시 계산한다. 짧은 값은 그 폭에서 가운데 정렬하고, 빈 인자는 `()`로 붙인 뒤 남는 폭을 괄호 밖에 둔다. 기존의 불필요한 내부 공백을 폭 기준으로 재사용하지 않는다.
8. production 구조 분해의 `{ }`는 고정 폭 셀로 유지한다. 가져오는 호출 가능 식별자는 함수 이름이므로 `{` 뒤 한 칸에서 왼쪽 정렬하고 남는 폭을 오른쪽에 둔다. 닫는 `}`와 그다음 `= await` 열은 모든 행에서 맞춘다.
9. 한 줄 화살표 함수의 본문 `{ }`는 값 셀이 아니라 실행 블록이다. 여는 `{`와 마지막 실행문의 시작 열은 맞추되, 마지막 호출은 실제 길이로 끝낸다. 종결 `;` 뒤 한 칸만 두고 `}`로 닫으며 닫는 중괄호 열을 맞추기 위한 후행 공백은 추가하지 않는다.
10. production 의존성은 실행·조회·선택·출력처럼 역할별로 묶는다. 기준 파일에서 수락된 `const { } = await import(...)`와 실행 셀의 축은 임의로 여러 줄로 해체하지 않는다.
11. 우측 보조 설명은 마지막 열린 셀이다. 같은 선언 표에서 역할 구획이 달라도 `//` 시작 열은 맞춘다. `Promise< >` 같은 앞 셀의 최소 폭은 유지하고 문장 종결자 뒤의 바깥 여백으로만 `//`를 이동한다. 설명은 한 칸 뒤에서 왼쪽 정렬하며 설명 길이를 맞추기 위한 오른쪽 공백은 추가하지 않는다. 등록되지 않은 Code-ID를 만들지 않는다.
12. 반복 구현은 한 줄이 기본이다. 한 줄이 지나치게 길어질 때만 의미 경계에서 두 줄로 내리고, 짧은 행까지 일괄적으로 펼치지 않는다.
13. 의존성 인터페이스는 하나로 유지하고 `// Run`, `// List`, `// Select`, `// Write` 구획 주석으로 역할을 나눈다. 타입을 역할별 인터페이스로 쪼개지 않는다.
    각 역할 구획은 독립된 표다. `( )`, `Promise< >`, `;`, `//` 폭은 구획 안의 실제 최장값으로만 계산하며 다른 구획의 긴 타입을 폭 기준으로 가져오지 않는다.
14. 표 폭을 줄이기 위한 목적으로 함수 시그니처를 이름 있는 로컬 타입으로 빼지 않는다. 같은 비교 블록에서는 가장 긴 실제 시그니처를 그대로 폭 기준으로 삼는다. 타입 분리는 독립된 도메인 의미나 재사용 계약이 있을 때만 한다.
15. 인라인 객체 타입을 새로 반복하기 전에 같은 의미를 소유한 기존 Domain·Port 타입을 찾고 재사용한다. 타입 이름을 붙이는 목적은 행을 줄이는 것이 아니라 이미 존재하는 계약의 의미를 드러내는 것이다.
16. 표 위에 컬럼 헤더 주석을 둘 때는 `NAME`, `PARAMETERS`, `RETURN TYPE`처럼 ASCII 라벨만 사용한다. 한글 표시 폭은 터미널과 에디터에 따라 달라질 수 있으므로 열 위치의 기준 데이터로 사용하지 않는다. 헤더의 문법 경계와 하위 셀 시작 열은 실제 코드 행과 같아야 한다.
17. 긴 예외 요소를 발견하면 정렬 전에 정의·호출자·테스트를 확인한다. 모든 호출에서 같은 상수로 전달되는 매개변수처럼 소비자가 선택하지 않는 정보는 인터페이스에서 제거하고 구현 어댑터 안에 결속할 수 있는지 검토한다.
18. 구조 단순화는 의미와 타입 안전성을 보존해야 한다. 필수 입력을 없애거나 서로 다른 계약을 하나로 뭉치거나, 단지 짧게 보이기 위해 타입 별칭을 추가하는 것은 간결화로 보지 않는다.
19. 통일성은 모든 행에 가장 긴 예외의 폭을 강요하는 것이 아니다. 기본 행과 다른 요소가 표 전체를 넓히면 해당 요소를 별도 행·별도 표·내부 구현으로 옮길 수 있는지 먼저 검토하고, 의미상 분리할 수 없을 때만 공통 폭에 포함한다.
20. `?`는 제거 대상 표시가 아니라 값의 생략이 계약에 포함된다는 뜻이다. 입력 경계에서 실제 생략이 가능할 때만 유지하고, 내부에서는 조건 검사·기본값·정규화로 가능한 한 빨리 구체 타입으로 좁힌다. 공개·경계 인터페이스에서 생략 의미가 이름만으로 분명하지 않으면 속성 바로 앞의 짧은 `/** JSDoc */`이 그 의미를 소유하고 실제 property hover로 노출을 확인한다.
21. 같은 부재 상태에 `null`과 `undefined`를 섞지 않는다. 사용자 선택 취소처럼 명시적인 결과는 `null`, 객체 속성의 미제공은 `?`로 표현한다. 계층 사이에서 둘을 변환하기 위한 코드가 생기면 경계 계약을 다시 검토한다.
22. 배열 인덱스의 `!`와 넓은 값의 `as`는 먼저 지역 변수와 조건 분기로 제거할 수 있는지 확인한다. 런타임 근거 없이 검사기를 침묵시키는 단언은 간결화가 아니다.
23. `void`, `string`, `boolean`처럼 이미 짧고 의미가 분명한 primitive는 별칭화하지 않는다. 길고 반복되는 복합 타입에 독립된 도메인 의미가 있을 때만 짧고 구체적인 이름을 붙인다.
24. 이름 있는 타입과 공개 optional 속성의 보조 설명은 선언 바로 앞의 `/** JSDoc */`이 소유한다. 문자열 리터럴과 우측 `//`는 hover 설명으로 간주하지 않으며 TypeScript LSP의 `textDocument/documentSymbol`로 실제 선언을 찾은 뒤 `textDocument/hover` 응답의 설명 노출을 확인한다. 같은 이름의 선언은 `name#occurrence`로 명시하고 모호하거나 JSDoc이 없는 요청은 실패시킨다.
    단, 외부로 export하지 않는 로컬 타입 별칭이 연속될 때는 선언을 `type / 이름 / = / 실제 타입 / ; / // 설명` 표로 묶는다. 이 설명은 파일 내부 탐색용이며 공개 hover 계약을 대신하지 않는다.
25. 반복 행의 최소 공통형을 먼저 기록한다. 기본형에 없는 타입 수식자·추가 매개변수·래퍼·부재 표현·변환 코드가 나타나면 즉시 폭 기준으로 채택하지 않고 이질 요소로 분류한다.
26. 이질 요소는 `필수 도메인 정보`, `경계에서만 필요한 정보`, `구현 세부사항`, `중복 표현` 중 하나로 판정한다. 경계 정보는 경계 가까이에, 구현 세부사항은 내부에 두며, 중복 표현은 제거한다.
27. 구조 변경은 짧아 보이는지만으로 수락하지 않는다. 변경 뒤 기본형이 실제로 더 균일해졌고 행동·타입 안전성·계층 책임이 보존됐을 때만 간결화로 수락한다.
28. `exactOptionalPropertyTypes`가 꺼진 상태의 `property?: T`는 명시적 `property: undefined`도 허용한다. 호출부에서 속성 생략과 명시적 `undefined`를 별도로 조사하고 같은 부재 의미라면 속성 생략 하나로 통일한다. 서로 다른 의미가 확인된 경우에만 `| undefined`를 명시 계약으로 유지한다.
29. optional 엄격화는 `audit-optional-types.ts`를 읽기 전용 마이그레이션 게이트로 먼저 실행한다. 기본 실행은 오류 0건을 요구하고, `--max-errors <현재 기준선>`은 오류 증가를 실패시킨다. `--file <대상 파일>`은 전역 판정을 유지하면서 그 파일의 행·열·오류 코드·진단 문장을 별도로 보고한다. 전체 0건과 관련 행동 테스트를 확인한 뒤에만 `tsconfig.json`에 활성화하며, 일괄적으로 `| undefined`를 덧붙여 통과시키지 않는다.
30. 불확실성 감사의 모수는 `audit-type-uncertainty.ts --file <대상 파일>`이 TypeScript AST에서 추출한다. optional 속성·매개변수·메서드·튜플·타입, `null`, `undefined`, non-null assertion, definite assignment, `as`, angle-bracket assertion을 서로 다른 종류로 보고한다. 논리 부정과 조건 연산자는 목록에 포함하지 않으며, 출력을 자동 제거 목록으로 간주하지 않고 정의·호출자·테스트로 각각 판정한다.
31. 저장소 전체 흐름 지도는 `docs/`의 감사 문서가 소유한다. 제품 파일에 수동 함수 지도나 그 구조를 고정하는 테스트를 요구하지 않는다.
32. 공개 Port·Domain 계약은 compact TypeScript 표기를 기본으로 한다. JSDoc·optional capability·수명주기 책임이 섞인 메서드 목록에 역할 주석을 추가해 가짜 표를 만들거나, `Promise< >`의 닫는 `>`를 맞추려고 타입 내부를 공백으로 늘리지 않는다.
33. 같은 역할의 객체 배열은 객체 하나를 한 행으로 취급한다. 선택 속성의 생략이 단지 표현 기본값일 뿐이면 모든 행을 동일한 속성 셀로 정규화하고 `{`, 각 `:`, 각 `,`, `}`를 실제 최장값 기준으로 맞춘다. 생략 자체가 도메인 의미이면 명시값으로 덮지 않고 별도 표로 분리한다.
34. 객체 기반 열 명세와 그 열에 들어갈 데이터 행 생성은 독립된 표다. 복잡한 호출 인자 안에 두 표를 중첩하지 않고 각각 이름 있는 지역 값으로 분리하며, 호출부는 `{ columns, rows }`처럼 최소 구성으로 유지한다.
35. 종결 `;`는 더 이상 예외로 붙이지 않는다. 같은 표 안에서는 다른 열과 동일하게 실제 최장 값 기준으로 열을 맞춘다. `;` 뒤에 닫는 `}`가 바로 오는 한 줄 실행 블록(규칙 9)은 별도 사례로 유지하고 이 규칙으로 덮지 않는다.
36. 비교 대상 행이 없는 단독 문장(같은 역할의 반복이 3행 미만이라 표가 되지 않는 경우)은 세로로 쪼개 정렬하지 않는다. `if (조건) 실행() return`처럼 원래 한 줄로 읽히던 짧은 흐름은 압축된 한 줄 형태를 우선한다.
37. 인터페이스와 클래스의 멤버 선언은 한 멤버가 한 물리 행을 소유한다. 같은 행에 여러 속성·메서드 선언을 `;`로 이어 붙여 표의 행 경계를 숨기지 않는다. 짧은 공개 계약도 이 규칙의 예외가 아니다.

## 열 기준점

반복 블록을 작성하기 전에 비교할 셀과 문법 축을 정한다. 객체 배열 외에도 등록 객체와 지역 계산 선언이 적용 대상이다.

- **등록 객체**: 항목 하나가 한 행이다. `속성명 | : | 실행식`으로 나누고 `:`와 실행식 시작 열을 맞춘다. 반복되는 `new` 또는 `scroll(new …)` 안에서는 생성자 이름과 인자 괄호를 하위 셀로 비교한다. 단독 예외 래퍼는 다른 행의 폭 기준으로 강요하지 않는다.
- **연속 선언**: 같은 계산 단계의 `const | 이름 | = | 계산식`에서 `=`와 계산식 시작 열을 맞춘다. 다중 행 배열 초기화는 별도 표이며, 콜백 안의 지역 선언이나 다른 계산 단계와 축을 공유하지 않는다.
- **검사 범위**: 변경 diff에서 위 블록을 빠짐없이 식별하고 블록별 줄 범위·토큰·기대 열을 측정기에 전달한다. 일부 블록 통과는 파일 전체 통과가 아니다. 미검사 블록은 미검사로 남긴다.

## 열 정렬 검사 단계

각 단계가 통과한 뒤 다음 단계로 간다. 뒤 단계의 공백을 먼저 조정해 앞 단계의 경계를 흐리지 않는다.

1. **비교 블록 확정**: 같은 역할과 문법 구조를 가진 연속 행만 하나의 표로 묶는다.
2. **기본형 기록**: 가장 흔한 정상 행들이 공유하는 최소 구조와 읽기 순서를 표의 기본형으로 기록한다.
3. **예외 요소 판정**: 가장 긴 행의 타입·매개변수·반환값이 필수 계약인지, 어댑터 내부로 결속하거나 중복을 제거해 줄일 수 있는 구현 세부사항인지 정의와 호출자를 확인한다.
4. **구조 간결화**: 이질 요소를 필수 도메인 정보·경계 정보·구현 세부사항·중복 표현으로 분류하고 제거, 내부 결속, 기본값 정규화, 별도 표 분리를 순서대로 검토한다.
5. **타입 불확실성 판정**: `?`, `null`, `undefined`, `!`, `as`를 찾아 실제 부재 계약, 중복 표현, 제거 가능한 단언으로 분류한다. 의미 있는 복합 타입만 이름과 JSDoc을 갖게 한다.
   `exactOptionalPropertyTypes`가 꺼져 있으면 optional 속성 생략과 명시적 `undefined` 전달을 따로 집계하고, 현재 파일에서 같은 의미인 전달은 속성 생략으로 정규화한다.
6. **최외곽 경계 정렬**: 식별자 뒤 `:`, 바깥 `( )`, `=>`, 함수 본문의 바깥 `{ }`, 문장 끝 `;`, 우측 `//`의 열을 왼쪽에서 오른쪽 순으로 확정한다.
7. **폭 계산**: 각 셀의 폭은 구조 간결화 뒤 보존된 실제 내용이 요구하는 최소 폭으로만 계산한다. 여러 매개변수는 먼저 줄별로 나누고 그중 가장 긴 줄을 기준으로 삼는다. 빈 매개변수 목록은 `()`로 닫고 다음 문법 경계까지 바깥 여백으로 열을 맞춘다.
8. **내부 구문 정렬**: 외곽 경계가 고정된 뒤 `import`, `from`, `const`, `= await`, 마지막 `await`·`return`처럼 반복되는 내부 구문의 시작 열을 맞춘다.
9. **내용 배치**: 기능·함수 이름과 실행 셀은 왼쪽 정렬한다. 빈 `()`와 배열 표식 `[]`는 내부 공백 없이 묶는다. 객체 배열은 여는 `{`와 닫는 `}`까지 하나의 외곽 행으로 측정하고, 보존된 모든 속성의 `:`와 구분 `,`가 같은 열인지 확인한다.
10. **초과 행 처리**: 120열을 넘는 새 행은 의미 경계 분리를 검토한다. 기준 파일의 수락된 그리드는 사용자 확인 없이 변경하지 않는다.
11. **실측 검증**: 표시 폭과 hover 측정기로 선택한 짧은 반복 블록과 JSDoc 노출을 확인한다. 코드 실행·타입 검사·대상 테스트로 동작이 바뀌지 않았음을 확인한다.

## 폐기 규칙

- 가장 긴 행보다 먼 임의 열에 `=>`나 주석을 배치하지 않는다.
- 서로 다른 의미의 문장을 단지 토큰이 같다는 이유로 파일 전체에서 한 열에 강제하지 않는다.
- 관련 없는 블록끼리 하나의 최대 폭을 공유하지 않는다. 셀 폭은 비교 대상인 현재 블록 안에서만 계산한다.
- 자동 포매터처럼 저장소 전체를 한 번에 바꾸지 않는다.
- 비교 효용이 없는 중앙 정렬이나 실제 최장 데이터보다 넓은 임의 폭을 만들지 않는다.

## 인터페이스 분리 기준

`CliDependencies`처럼 하나의 소비자가 한꺼번에 받는 의존성은 단일 인터페이스로 유지한다.

- `Run`: 실행을 시작하거나 명령을 위임한다.
- `List`: 여러 항목을 조회한다.
- `Select`: 사용자 선택을 받는다.
- `Write`: 사용자에게 출력한다.

각 역할은 `// Run` 같은 구획 주석으로 드러낸다. 구획 안에서는 실행 흐름 순서를 사용하며 알파벳순으로 재배치하지 않는다. 존재하지 않는 역할을 채우기 위해 빈 `Read` 같은 구획을 만들지 않는다.
