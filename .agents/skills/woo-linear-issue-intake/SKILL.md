# WWW Linear Issue Intake

**요청 → 기존 내용·가이드 확인 → 넣을 위치와 처리 방식 결정 → Candidate 작성 → 검증·렌더** 순서로 진행한다. GitHub Issue에는 별도 `woo-issue-intake`를 사용한다. 외부 반영과 재조회는 `woo-linear-publish`가 소유한다.

이 스킬은 99_www 프로젝트의 Linear 분류 절차를 소유한다. 상위 방법론 정본은 `~/.codex/woo.yaml`의 workspace_root를 통해 읽는다. 상위 계약을 이 파일에 복제하지 않는다.

## 1. 기존 맥락 확인

제목·번호·하위 구조를 만들거나 정리할 때는 [제목 계층 규칙](../woo-linear-title-hierarchy/SKILL.md)을 먼저 적용한다. 기능별 예외 처리·테스트의 위치와 반영 전후 계약 검증도 이 규칙이 소유한다.

생성 도구를 호출하기 전에 다음 자료를 읽는다.

- 요청의 목적·원하는 결과·사용자가 지정한 위치와 기존 결정.
- 대상 Linear Project의 설명·Milestone 및 해당 기능의 부모, 형제, 직계 하위 이슈. 제안 부모의 상위 경로를 Project까지 확인한다.
- 의미가 겹치는 기존 이슈. 활성뿐 아니라 완료·취소·보관된 관련 항목도 검색한다. 목록이 잘렸으면 본문을 개별 조회하고, 페이지가 남으면 계속 읽는다.
- [개발 흐름](../../../docs/planning/linear-development/DEVELOPMENT_FLOW.md), [제품 경계](../../../docs/planning/linear-development/ARCHITECTURE.md), 해당 기능의 코드·ID 원장·관련 설계. 새 사용자 결정과 역사적 초안을 구분한다.

조회가 실패하거나 필요한 본문이 없으면 “기존 항목 없음”으로 판정하지 않는다. 확인 가능한 초안은 작성하되, 위치가 확인될 때까지 외부 생성을 보류한다.

## 2. 처리 방식과 위치 결정

| 기존 내용과 요청의 관계 | 처리 |
| --- | --- |
| 같은 결과·같은 수락 단위가 이미 있음 | 기존 이슈 본문 보완. 새 이슈를 발급하지 않음 |
| 한 기능의 세부 조건·단순 구현 단계·개별 테스트 | 해당 이슈의 체크리스트 또는 검증 항목 보완 |
| 기존 기능 안에서 독립적으로 구현·검증·종료할 결과 | 그 기능 이슈 바로 아래에 새 하위 이슈 |
| 여러 기능이 함께 사용하는 공통 실행·저장 기반 | System의 기존 책임 이슈 아래. 여러 소비 화면에는 관련 링크 |
| 특정 업무의 수행 순서·업무 수락 정책 | Workflow의 해당 업무 아래 |
| 기존 분류 어디에도 자연스럽게 들어가지 않음 | 새 상위 분류가 필요한 이유와 대안을 제시하고 사용자 결정을 받음 |

부모는 **기능의 책임**, `relatedTo`는 **다른 기능과의 연관**, `blockedBy`는 **실행 선행 조건**으로 정한다. 같은 파일을 수정하거나 의존한다는 이유만으로 부모를 정하지 않는다. 라벨은 실제 parentId를 대신하지 않는다.

사용자가 만든 상위 분류는 유지한다. 세부 작업을 기존 분류의 형제로 승격하거나, TUI 소비 기능을 공통 DB 작업이라는 이유로 System 아래에 넣지 않는다. 여러 책임이 섞인 요청은 결과 단위로 나눠 각 기존 부모를 찾는다.

사용자가 명시적으로 한 이슈를 요청했는데 결과별 분리가 필요하면, 분할 이유와 각 부모 후보를 먼저 확인한다. 스킬의 분류 기준으로 사용자의 명시적 묶음 지시를 자동 변경하지 않는다.

현재 구조를 코드처럼 고정 복사하지 않고 MCP로 재조회한다. 2026-09-06 적용 사례: Workbench의 기존 Chat·Layout·Tracer·Todo 분류를 유지하고 T-note·Composer는 Chat 하위로 배치했다. 이 사례는 이후 사용자의 구조 변경보다 우선하지 않는다.

## 3. 생성 전 위치 기록

본문을 쓰기 전에 작업 기록에 다음을 남기고 사용자에게 간단히 보여준다. 여러 건은 한 표로 묶는다.

| 항목 | 남길 내용 |
| --- | --- |
| 요청 | 어떤 문제·결과를 추적하는가 |
| 처리 | 기존 본문 보완 / 새 하위 이슈 / 기존 이슈 이동 |
| 위치 | Project → 상위 분류 → 기능 부모 → 대상. 실제 ID 포함 |
| 대조 | 읽은 부모·형제·관련 이슈 ID, 조회 시각, 중복 아닌 이유 |
| 가이드 | 적용한 문서·사용자 결정과 책임 판정 이유 |
| 메타데이터 | 라벨, Milestone 유지/지정/미지정과 그 근거 |

사용자가 이미 위치와 범위를 지정했거나 승인한 계획이 있으면 그 범위에서 진행하며 반복 승인을 요구하지 않는다. 위치 후보가 여러 개이거나 기존 상위 분류를 바꿔야 할 때만, 실제 후보와 추천 이유를 선택 질문으로 확인한다. “진행”은 관련 없는 상위 구조 개편의 승인이 아니다.

## 4. 본문 작성

RPA 고객 업무의 Project·Task Description은 [RPA Description 계약 v1](../../../docs/workflows/RPA_DESCRIPTION_CONTRACT.md)의 고정 구조와 엔진을 사용한다. 아래 일반 이슈의 짧은 본문 규칙은 해당 프로필의 Unit 기술·코드·Step·케이스 필드를 축약하는 근거로 쓰지 않는다.

- 제목은 목적·문제·결과가 드러나는 한국어 문장으로 쓴다. 기능·유형은 기존 라벨을 우선 재사용한다.
- 부모 본문은 목적·공통 원칙·통합 완료 조건을 소유한다. 하위 이슈의 화면 구성·구현 단계·검증 상세를 복제하지 않는다.
- 실행 하위 이슈는 목적, 포함 범위, 관측 가능한 완료 조건, 코드·관련 ID·검증 근거를 담는다. 코드 존재와 실제 수락 상태를 구분한다.
- 새 하위 이슈만으로 전체 부모의 범위가 완성됐다고 쓰지 않는다.
- `@unit`, `@linear` 등 코드 어노테이션은 inline code로 써서 Linear 사용자 mention으로 변환되지 않게 한다.

## 5. Candidate와 완료 판정

1. `schemas/artifact-candidate.schema.json`의 `linear-issue` Candidate를 만든다. 새 이슈는 확인한 parentId·Project, 기존 이슈는 UUID와 변경 전 필드를 `target`과 `expectedBefore`에 넣는다.
2. 본문은 `content`의 `title`, `purpose`, `included`, `excluded`, `done`, `connections`로만 표현한다.
   RPA Description은 예외로 계약 v1의 `linear-project / rpa-project-v1` 또는 `linear-issue / rpa-task-v1` Candidate를 사용한다. 자유 Markdown을 끼워 넣지 않고 공통 엔진을 호출한다.
3. `bun run artifact:control -- validate --candidate <path> --actual-before <readback>`과 `render`를 실행한다. 기능 계층 변경은 제목 계층 스킬의 오프라인 검증도 통과시킨다.
4. 처리 방식·위치·중복 대조·렌더 전체·digest를 제시한다. 완료는 게시 가능한 Candidate가 만들어진 상태이며 Linear 상태는 아직 바뀌지 않았다.

사용자가 게시를 승인하면 `woo-linear-publish`로 넘긴다. Candidate 작성 승인은 외부 변경 승인이 아니다.
