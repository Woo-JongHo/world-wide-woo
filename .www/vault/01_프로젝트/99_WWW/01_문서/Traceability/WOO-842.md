# 목적

layer-first 최상위 구조 때문에 한 capability의 계약·실행·표시를 찾기 위해 여러 폴더를 횡단하던 비용을 줄이고, v0.1.0 코드 구조를 제품 언어인 TUI·System·Workflow에 맞춘다.

# 배경과 결정

- 최상위 탐색 축은 `src/tui`, `src/system`, `src/workflows`다.
- 단순 평탄화 대신 `system/contracts`, `system/services`, `system/adapters`로 순수 계약과 IO seam을 유지한다.
- System은 Workflow를 import하지 않는다. Workflow는 `src/system/public.ts`의 공개 계약만 사용한다.
- 현대 TUI는 Workflow 공개 entry와 System의 읽기 전용 projection·command interface만 사용한다.
- concrete adapter 선택과 legacy Router 조립은 `src/app.ts`만 소유한다.
- 범용 Workflow Engine은 만들지 않고 실제 개발 기록 규칙만 `src/workflows/tui-development`로 옮긴다.

WOO-842는 WOO-672의 하위 이슈이며 World Wide Woo project의 v0.1.0 milestone에 속한다. 상태는 Backlog, label은 System·Improvement이고 WOO-671·WOO-673과 관련된다.

# 상세 동작

전수 before/after 124개 경로와 단계별 rollback은 `docs/planning/linear-development/V010_CAPABILITY_MIGRATION_PLAN.md`가 소유한다. `src/system/public.ts`, `src/workflows/tui-development/index.ts`, `src/tui/index.ts`가 소비 경계를 제공한다. `test/architecture.test.ts`는 최상위 축, 계약 순수성, 역방향 import 금지, app-only adapter 선택, legacy 격리, cycle 부재를 검사한다.

구조 이동은 지속 기능 identity 변경이 아니다. `Code-001`부터 `Code-013`까지 key, UUID, 대표 symbol을 유지하고 원장의 location만 새 경로로 옮겼다. WOO-842는 이 13개 Unit 모두에 `implemented-by`로 연결하며 대표 상세 기록 frontmatter는 원장 계약 자체인 `Code-006`을 사용한다. SQLite와 Development Map은 수정된 두 원장에서 재구축한다.

# 예외

- legacy Multi-provider Router는 기능 삭제 없이 `src/tui/legacy`에 격리한다.
- Workflow 내부 scanner, Vault writer, SQLite store, map builder는 해당 Workflow의 IO adapter이며 공개 entry에서 노출하지 않는다.
- 2026-09-06의 `main` 코드 위치를 증거로 기록한 기존 Chat 노트의 링크는 역사 기록이므로 이전 layer 경로를 유지한다. 현재 위치를 주장하는 Traceability·Code note만 새 경로로 갱신한다.
- WOO-842 본문과 WOO-672 직계 하위 pagination은 Woo Linear MCP로 재조회했다. 전체 프로젝트 37개 이슈 snapshot은 별도 strict acquisition 입력이므로 부분 readback으로 대체하지 않는다.
